## Пространства имён и структура файлов

Типы размещать по смысловому назначению. Если у класса, модели, DTO, интерфейса
или другого типа нет отдельной предметной или функциональной категории внутри
модуля, его файл размещать в корне проекта. Сам по себе вид типа или статус
публичного контракта не является основанием для подпапки.

Не создавать общие папки `Contracts`, `Models`, `DTOs`, `Interfaces` и аналогичные
только для группировки по виду типа. Если тип относится к конкретной подсистеме
(`Frames`, `Sessions`, `Hosting` и т. п.), размещать его в папке этой подсистемы
вместе со связанными типами независимо от того, интерфейс это, DTO или реализация.
Не придумывать искусственную категорию, чтобы избежать размещения в корне.

Это правило относится к структуре файлов внутри проекта. `TrueMoon.Contracts` —
отдельный пакет общих контрактов, базовых моделей и интерфейсов, предназначенных
для взаимодействия модулей TrueMoon; его назначение не ограничивается App.
Специфичные для отдельного модуля типы остаются в этом модуле: статус интерфейса
или DTO сам по себе не является основанием для переноса в `TrueMoon.Contracts`.
Общая сборка не должна зависеть от конкретных реализаций модулей или providers.
Внутри неё действуют те же правила смысловых категорий и namespace.

Применять правило при создании и целенаправленной реорганизации типов; перенос
существующего публичного типа требует обновления namespace и ссылок с учётом
совместимости API.

В исходном C# коде namespace должен соответствовать реальному расположению файла
относительно корня проекта. За основу брать `RootNamespace` из `.csproj`, а если
он не задан — имя проекта. Каждая подпапка добавляет соответствующий сегмент
namespace с сохранением названия и регистра.

Например, `TrueMoon.Aether/Frames/FrameSession.cs` должен использовать
`namespace TrueMoon.Aether.Frames;`, а файл в `TrueMoon.Aether/Hosting/` —
`namespace TrueMoon.Aether.Hosting;`.

Не оставлять классы из подпапок в корневом namespace и не пропускать сегменты
пути ради сокращения имени. При создании или перемещении файлов одновременно
обновлять namespace, связанные partial declarations, using и ссылки на типы.

## Подключение модулей к App

Штатный путь подключения функциональных модулей TrueMoon, предоставляющих сервисы,
конфигурацию, фоновые задачи или owned resources, — через `TrueMoon.App`.
Модуль должен предоставлять публичное расширение `IAppConfigurationContext`
(`UseModule(...)`, `AddModule(...)` или аналог по назначению), вызываемое из
`App.Builder(...).Setup(...)`, `App.Build(...)` или `App.RunAsync(...)`.

В этой точке валидировать/фиксировать options, регистрировать сервисы в resolver
приложения и согласовывать start/stop/drain/dispose с App lifecycle. Явно определять
ownership, поведение при failed startup/cleanup и повторном подключении; исключать
двойное освобождение через DI aliases. Low-level типы могут использоваться отдельно,
но пример в ManualTests не заменяет публичную точку подключения самого модуля.

Для integration использовать общие App contracts из `TrueMoon.Contracts`;
конкретный bootstrap/UI/provider добавлять в зависимости только по необходимости.
Общие utilities/contracts без собственного lifecycle не требуют фиктивного UseX.

## DI и создание систем и сервисов

Штатный DI-контейнер TrueMoon — Cobalt. Все системы и сервисы приложения должны
создаваться и предоставляться через DI и внедрённые фабрики `IFactory<T>`
(с runtime arguments — `IFactory<T, TArguments>`).
Регистрации размещать в публичной точке подключения модуля к App; реализации,
options и lifetime выбирать при сборке графа приложения.

Зависимости сервисов передавать явно через конструктор. Прямой `Resolve` и доступ
к `IServiceResolver` сосредоточивать в bootstrap/composition root и инфраструктуре
фабрик/DI adapters. Не передавать контейнер прикладным системам для поиска своих
зависимостей и не использовать глобальный service locator.

Для отложенного, повторного или параметризованного создания систем и сервисных
объектов внедрять `IFactory<T>`; саму фабрику получать через DI. Это относится,
например, к окнам, сессиям и операциям со своим временем жизни. Ручное создание
сервисов через `new` допустимо внутри реализации фабрики или DI registration
factory, где собирается граф, но не как обход DI в прикладном коде. Параметры
создания оформлять явными типизированными аргументами/options.

Для каждого сервиса и результата фабрики явно определять lifetime, владельца
и порядок stop/drain/dispose, включая неудачное создание и cleanup. Результат
`IFactory<T>.Create` не становится автоматически owned объектом контейнера:
это определяется реализацией фабрики и контрактом потребителя. Короткоживущие
ресурсы окна/сессии не удерживать до завершения App; не допускать двойного
освобождения через aliases или одновременное владение контейнером и потребителем.

DTO, значения, сообщения, коллекции и отдельные элементы UI-дерева допускают
обычное создание через `new`; регистрировать каждый объект данных в DI не нужно.
Низкоуровневые ресурсы создавать внутри отвечающей за них фабрики/владельца.
В игровых и render циклах использовать уже внедрённые зависимости, не выполнять
повторный resolution сервисов на каждый кадр или элемент.

Общие DI-контракты и `IFactory<T>` использовать из `TrueMoon.Contracts`;
module-specific factory contracts оставлять в своём модуле. Зависимость каждой
сборки от реализации Cobalt не требуется. Не вводить новые scopes, factory APIs
или async activation только ради этого правила: такие возможности требуют
отдельной задачи и согласованного ownership contract.

Применять правило при создании и целенаправленной переработке систем и сервисов.
Существующий Microsoft DI adapter и provider-specific проверки сохранять;
массовая миграция существующих consumers не входит в фиксацию этого правила.
Адресные изменения проверять на соответствие DI generation, lifetime и lifecycle.

## UI направление

### View, данные и оформление

Штатный подход для новых и целенаправленно перерабатываемых экранов — типизированный
`View<TData>` с Fluent-композицией, отдельные Data/ViewModel и отдельный класс
`IViewStyle<TView>`. View описывает дерево, привязки и подключение действий.
Data/ViewModel хранит данные и состояние экрана, доступность действий, ошибки и
команды; не зависит от контролов, renderer, native handles или темы. Для простого
представления достаточно обычных данных: обязательный базовый ViewModel не нужен.

Оформление View и контролов объявлять через `IViewStyle<TView>`: корень, явно
выбранные типизированные части и типизированные семантические роли. Динамические
элементы помечать ролями. Каждый вложенный View имеет собственную область стилей;
не обходить его внутреннее дерево из родительского стиля. Theme содержит общие
цвета, шрифты и размеры. Стили могут использовать Theme, но не изменяют состояние
модели, не запускают команды и не удерживают экземпляры View в общих сервисах.

Приоритет значений: local/binding → Style элемента → стиль View → Theme → default.
В Fluent-разметке оставлять композицию и осмысленные локальные переопределения;
общие цвета/отступы/шрифты не дублировать поверх вынесенного стиля. Замена/снятие
стиля и смена Theme обновляют существующие элементы, сохраняя фокус, выделение,
прокрутку и введённые данные. Полную перестройку дерева при каждом обновлении
ViewModel не использовать; динамические поддеревья меняются адресно.

ViewModel, style и `IFactory<TView>` регистрировать через DI; фабрика создаёт View
на UI owner thread, окно/родитель владеет View, dependencies заимствуются согласно
их lifetime. Сами контролы создаются View через Fluent API/конструкторы. Подписки
View снимаются при Dispose, ViewModel не освобождается заимствующим View.
Автоматическая миграция всех прежних consumers не требуется.
