## Уточнение решений

Если требования допускают несколько существенно разных решений и имеющихся
указаний недостаточно для выбора, уточните намерение пользователя до изменений,
которые от этого выбора зависят. Укажите, какое поведение, публичный контракт
или объём работ изменится в зависимости от ответа.

Если вопрос требует развёрнутого ответа и есть несколько подходящих вариантов,
предложите два или три варианта. Для каждого кратко объясните, когда он подходит
и что даёт или усложняет. Назовите рекомендуемый вариант и причину выбора.

## Версия C#

Для штатных проектов и генерируемого C# используйте последнюю стабильную версию
языка, поддерживаемую SDK из [global.json](global.json). Общий
[Directory.Build.props](Directory.Build.props) задаёт `LangVersion=latest`.
SDK выбирается с `allowPrerelease=false`. Новые стабильные возможности языка
можно использовать в исходниках и в выводе генераторов. Обновления SDK проводите
через общий профиль сборки. Точные или старые версии C# сохраняйте в явных
профилях совместимости.

## Версионирование поставок

Принято 15.11.2026. Формат версии продукта/пакетов —
`x.yyMM.d.rev[-postfix]`, например `1.2611.15.1-alpha`.

- `x` — поколение продукта/API; менять только по явному решению владельца.
  При первом переходе со старой схемы использовать `1`, сохраняя стадию `alpha`.
- `yyMM` и `d` — год/месяц и день по **UTC**; день записывать без ведущего нуля.
- `rev` — общий для всех postfix счётчик поставок данного репозитория за эту
  дату: первая — `1`, следующая — `2`; при новой дате начинать с `1`.
- Postfix — `alpha`, `beta` или `rc`; отсутствие postfix означает стабильную
  поставку. Стадию менять только по явному решению, не выводить её из passing
  тестов. Смена стадии не сбрасывает `rev`.

Пример последовательности: `1.2611.15.1-alpha` → `1.2611.15.2-alpha` →
`1.2611.16.1-alpha` → `1.2611.16.2-beta` → `1.2611.16.3-rc` → `1.2611.16.4`.

После завершённого набора изменений production-кода, генераторов, зависимостей,
native-библиотек, шейдеров, поставляемых ресурсов либо влияющих на артефакты
build/pack/publish правил агент обязан обновить общую `Version` в указанном ниже
`Directory.Build.props`. Один набор изменений — одно повышение версии, а не
повышение на каждый файл, промежуточную правку, тест или коммит внутри задачи.
Только документация/планы/инструкции либо только тесты не требуют повышения;
повторная поставка с изменённым содержимым пакета/дистрибутива требует новой версии.

Версию и дату зафиксировать **до финальной сборки, проверок и упаковки** и
использовать согласованно во всех артефактах и evidence этой поставки. Повторная
сборка тех же зафиксированных входов, в том числе после полуночи UTC, сохраняет
версию. Изменённое содержимое уже опубликованной поставки получает новую версию;
существующие пакеты/immutable manifests не перезаписывать. Промежуточные локальные
QA-версии через `-p:Version` не заменяют обновление общей версии в репозитории.

Перед выбором номера сверить текущую версию рабочей копии и актуальной целевой
`main`; перед слиянием повторить сверку. Версия нового production-набора должна
быть выше обеих по правилам сравнения NuGet, а не по строковому сравнению или
только относительно старого merge-base. При совпадении номеров параллельных веток
координатор выбирает следующий `rev` и повторяет затронутую финальную проверку
на итоговой версии. Общую версию меняет один координатор задачи; участники
параллельной работы не повышают её независимо друг от друга.

Все собственные проекты одной поставки используют общую версию своего
репозитория. TrueMoon, Studio и игра ведут независимые счётчики; одинаковая схема
не требует одинаковых номеров и не обновляет автоматически версии зависимостей.
Сохранять существующие условия/переопределения `Version`; не добавлять повышение
номера на каждый запуск MSBuild. Версии ABI, протоколов, форматов документов,
ассетов и сторонних библиотек меняются по собственным правилам совместимости.
Не вводить отдельную политику AssemblyVersion/FileVersion только ради этой схемы.
Исторические версии, manifests и результаты проверок не переписывать.

Эта документационная фиксация не меняет текущую `Version`; первый следующий
production-набор обязан перейти на принятую схему до финальной проверки.

Источник версии — [Directory.Build.props](Directory.Build.props), общий для пакетов
TrueMoon. Сохранять изоляцию `_TrueMoonFrameworksOnly` и профили независимых
consumers. Правило распространяется и на обновления native/зависимостей; их
верификацию выполнять по требованиям затронутого модуля.

## Пространства имён и структура файлов

Типы размещать по смысловому назначению. Если у класса, модели, DTO, интерфейса
или другого типа нет отдельной предметной или функциональной категории внутри
модуля, его файл размещать в корне проекта. Сам по себе вид типа или статус
публичного контракта не является основанием для подпапки.

Не создавать общие папки `Contracts`, `Models`, `DTOs`, `Interfaces` и аналогичные
только для группировки по виду типа. Если тип относится к конкретной подсистеме
(`Frames`, `Sessions`, `Hosting` и т. п.), размещать его в папке этой подсистемы
вместе со связанными типами независимо от того, интерфейс это, DTO или реализация.
Не придумывать искусственную категорию, чтобы избежать размещения в корне.

Это правило относится к структуре файлов внутри проекта. `TrueMoon.Contracts` —
отдельный пакет общих контрактов, базовых моделей и интерфейсов, предназначенных
для взаимодействия модулей TrueMoon; его назначение не ограничивается App.
Специфичные для отдельного модуля типы остаются в этом модуле: статус интерфейса
или DTO сам по себе не является основанием для переноса в `TrueMoon.Contracts`.
Общая сборка не должна зависеть от конкретных реализаций модулей или providers.
Внутри неё действуют те же правила смысловых категорий и namespace.

Применять правило при создании и целенаправленной реорганизации типов; перенос
существующего публичного типа требует обновления namespace и ссылок с учётом
совместимости API.

В исходном C# коде namespace должен соответствовать реальному расположению файла
относительно корня проекта. За основу брать `RootNamespace` из `.csproj`, а если
он не задан — имя проекта. Каждая подпапка добавляет соответствующий сегмент
namespace с сохранением названия и регистра.

Для проектов с контрактами и моделями, имя которых оканчивается на `.Contracts`
или `.Abstractions`, явно задавать в `.csproj` `RootNamespace` без этого
конечного суффикса. Например, для проекта `TrueMoon.Aether.Abstractions`:
`<RootNamespace>TrueMoon.Aether</RootNamespace>`. Имя проекта, сборки и пакета
от этого не меняется. Подпапки по-прежнему добавляют сегменты к `RootNamespace`.

Например, `TrueMoon.Aether/Frames/FrameSession.cs` должен использовать
`namespace TrueMoon.Aether.Frames;`, а файл в `TrueMoon.Aether/Hosting/` —
`namespace TrueMoon.Aether.Hosting;`.

Не оставлять классы из подпапок в корневом namespace и не пропускать сегменты
пути ради сокращения имени. При создании или перемещении файлов одновременно
обновлять namespace, связанные partial declarations, using и ссылки на типы.

## Подключение модулей к App

Штатный путь подключения функциональных модулей TrueMoon, предоставляющих сервисы,
конфигурацию, фоновые задачи или owned resources, — через `TrueMoon.App`.
Модуль должен предоставлять публичное расширение `IAppConfigurationContext`
(`UseModule(...)`, `AddModule(...)` или аналог по назначению), вызываемое из
`App.Builder(...).Setup(...)`, `App.Build(...)` или `App.RunAsync(...)`.

В этой точке валидировать/фиксировать options, регистрировать сервисы в resolver
приложения и согласовывать start/stop/drain/dispose с App lifecycle. Явно определять
ownership, поведение при failed startup/cleanup и повторном подключении; исключать
двойное освобождение через DI aliases. Low-level типы могут использоваться отдельно,
но пример в ManualTests не заменяет публичную точку подключения самого модуля.

Для integration использовать общие App contracts из `TrueMoon.Contracts`;
конкретный bootstrap/UI/provider добавлять в зависимости только по необходимости.
Общие utilities/contracts без собственного lifecycle не требуют фиктивного UseX.

## DI и создание систем и сервисов

Штатный DI-контейнер TrueMoon — Cobalt. Все системы и сервисы приложения должны
создаваться и предоставляться через DI и внедрённые фабрики `IFactory<T>`
(с runtime arguments — `IFactory<T, TArguments>`).
Регистрации размещать в публичной точке подключения модуля к App; реализации,
options и lifetime выбирать при сборке графа приложения.

Зависимости сервисов передавать явно через конструктор. Прямой `Resolve` и доступ
к `IServiceResolver` сосредоточивать в bootstrap/composition root и инфраструктуре
фабрик/DI adapters. Не передавать контейнер прикладным системам для поиска своих
зависимостей и не использовать глобальный service locator.

Для отложенного, повторного или параметризованного создания систем и сервисных
объектов внедрять `IFactory<T>`; саму фабрику получать через DI. Это относится,
например, к окнам, сессиям и операциям со своим временем жизни. Ручное создание
сервисов через `new` допустимо внутри реализации фабрики или DI registration
factory, где собирается граф, но не как обход DI в прикладном коде. Параметры
создания оформлять явными типизированными аргументами/options.

Для каждого сервиса и результата фабрики явно определять lifetime, владельца
и порядок stop/drain/dispose, включая неудачное создание и cleanup. Результат
`IFactory<T>.Create` не становится автоматически owned объектом контейнера:
это определяется реализацией фабрики и контрактом потребителя. Короткоживущие
ресурсы окна/сессии не удерживать до завершения App; не допускать двойного
освобождения через aliases или одновременное владение контейнером и потребителем.

DTO, значения, сообщения, коллекции и отдельные элементы UI-дерева допускают
обычное создание через `new`; регистрировать каждый объект данных в DI не нужно.
Низкоуровневые ресурсы создавать внутри отвечающей за них фабрики/владельца.
В игровых и render циклах использовать уже внедрённые зависимости, не выполнять
повторный resolution сервисов на каждый кадр или элемент.

Общие DI-контракты и `IFactory<T>` использовать из `TrueMoon.Contracts`;
module-specific factory contracts оставлять в своём модуле. Зависимость каждой
сборки от реализации Cobalt не требуется. Не вводить новые scopes, factory APIs
или async activation только ради этого правила: такие возможности требуют
отдельной задачи и согласованного ownership contract.

Применять правило при создании и целенаправленной переработке систем и сервисов.
Существующий Microsoft DI adapter и provider-specific проверки сохранять;
массовая миграция существующих consumers не входит в фиксацию этого правила.
Адресные изменения проверять на соответствие DI generation, lifetime и lifecycle.

## Единая конфигурация App и модулей

Штатный механизм настроек приложения — `TrueMoon.Configuration` и общие
контракты `IConfiguration` и providers из `TrueMoon.Contracts`, независимо от
Cobalt или Microsoft DI adapter. Источники, их приоритеты и явные переопределения
собираются в App/bootstrap/composition root. Детальный план унификации и перехода:
[CORE7](docs/core/PLAN.md#core7-unified-configuration).

Для новых и целенаправленно перерабатываемых настроек использовать общий слой:
источники → разрешение ключей и приоритетов → типизированные options → проверка →
регистрация через публичный `UseModule`/`AddModule` и DI. Сервисам передавать
проверенные options/неизменяемый снимок либо специализированный reader, когда нужны
динамические настройки. Не внедрять весь конфиг во все системы без необходимости,
не выполнять разбор, IO и поиск настроек на каждом кадре или элементе.

Не создавать независимые правила чтения args/environment/JSON и их приоритетов
в каждом модуле. Чтение настроек из ОС сосредоточивать в общих providers
и явных bootstrap adapters; получение PID, системных путей и других сведений об ОС
само по себе не является чтением настроек приложения. Bootstrap до создания App
использует общий минимальный reader/parser без построения App/DI, затем передаёт
проверенный неизменяемый результат в composition root. Служебные parent/session/
nonce/protocol identity не переопределяются обычными пользовательскими источниками.

Сохранить удобные типизированные configure callbacks модулей, явные factory runtime
arguments и ownership/lifecycle. Команды, документы сцены, форматы ассетов и изменяемое
состояние UI/игры не превращать автоматически в configuration providers.
Секреты и полное окружение не выводить в диагностику; в сообщениях указывать ключ
и источник ошибки, маскируя чувствительные значения.

Общий profile/App stage/reload реализован в CORE7.1–3, Core/Mithril adapters —
в CORE7.4, модульные schemas/UseConfigured helpers — в CORE7.5.
[Рабочее руководство](docs/core/CONFIGURATION_GUIDE.md),
[каталог стандартных ключей](docs/core/CONFIGURATION_KEYS.md),
[API и границы модулей](docs/core/CONFIGURATION_MODULES.md).
CORE7.6 завершил сверку документации и единой поставки App/child consumers; точные
configuration proofs не заменяют native/GPU/release acceptance.
В composition root явно добавлять точные schema instances и источники; модули
используют нейтральные schema/binding utilities из Contracts. Bootstrap adapters
остаются ограниченными и явными; недостающие возможности фиксировать в CORE7.
Сохранять совместимость CLI/env/JSON, identity/captures, проверки и process ownership.
Старые callbacks остаются совместимым путём; наличие инструкции не переводит
автоматически все приложения и не подтверждает native/release readiness.

## UI направление

Для проектирования, реализации и ревью экранов Argentis/Alloy используйте
проектный скилл [truemoon-ui](../.agents/skills/truemoon-ui/SKILL.md).
[Пример обозревателя](../.agents/skills/truemoon-ui/references/editor-hierarchy.md)
показывает Fluent-дерево, привязки, стиль и генерацию доступа к именованным частям.

### Проверки UI

Перед изменением UI читать [переиспользуемую инструкцию](docs/alloy/UI_TESTING.md).
По умолчанию начинать с UiSession/routed input и дополнять CPU raster, тестовым
host или native profile по контракту задачи. Computer Use не является обязательной
зависимостью UI-тестов. Отделять fake metrics от настоящего raster, опубликованное
host state от Win32-ввода, logical scale от physical DPI, CPU PNG от GPU present.
Сохранять ownership/cleanup и подтверждать observable state/побочные эффекты;
инструкция не объявляет виртуальный native backend или новые passing результаты.
Pixel/font/baseline policy — в [GOLDEN_TESTS](docs/alloy/GOLDEN_TESTS.md).

### View, данные и оформление

Штатный подход для новых и целенаправленно перерабатываемых экранов — типизированный
`View<TData>` с Fluent-композицией, отдельные Data/ViewModel и отдельный класс
`IViewStyle<TView>`. View описывает дерево, привязки и подключение действий.
Data/ViewModel хранит данные и состояние экрана, доступность действий, ошибки и
команды; не зависит от контролов, renderer, native handles или темы. Для простого
представления достаточно обычных данных: обязательный базовый ViewModel не нужен.

Собирайте Fluent-дерево в порядке чтения экрана. Объявляйте его через
`Content(data, ui => ...)` в конструкторе, а обработчики располагайте ниже.
Для View без модели используйте `Content(ui => ...)`. Для создания контролов
используйте `ui.Create<TControl>()`, перегрузку с аргументами или шорткаты
`ui.Text(...)`, `ui.Button(...)`, `ui.HStack(...)`, `ui.VStack(...)`.
Простое действие в
одну-две строки можно оставить лямбдой в дереве. Объявляйте контролы, привязки
и условия видимости на месте. Для новых Fluent-методов используйте `Property(value)` для
сеттеров, `On<Event>(handler)` для событий, `With<X>(...)` для подключения
и композиции. `Bind` и `BindTwoWay` оставляют направление привязки явным.
В цепочке `UiControl<TControl, TData>` для данных текущего View достаточно
селектора, например `.BindValueTwoWay(data => data.SearchText)`.
Контекстом может быть любая реализация `IDataContext<TData>`, которая уведомляет
о замене источника на UI owner thread. Для отдельного стабильного источника
передайте саму модель.
Готовая команда в цепочке подключается через `.WithCommand(data => data.Command)`.
Для наблюдения за текущей моделью используйте контекстный `ObservePropertyChanged`.
Обработчик получает уведомления из очереди UI. `synchronize` читает актуальное
состояние при attach и смене контекста. Кнопка и клавиатура используют одну команду.

Сгенерированная или явная фабрика вызывает `ViewCreation.Prepare(view, style)`
на UI owner thread. Конструктор получает зависимости и задаёт `DataContext`.
При первом attach View один раз выполняет фабрику из `Content(...)` через реестр
сессии, регистрирует части, вызывает `OnContentPrepared()` и применяет стиль.
В hook уже доступны части, attach-уведомления и первый layout ещё не прошли.
Возвращайте корень, созданный текущим `ui`, со всеми контролами, полученными
из этого контекста. Для адресной замены готового поддерева используйте
`SetContent`. Обычная сессия предоставляет встроенные фабрики. Прикладные
фабрики регистрируйте в `UiControlFactories` через `IFactory<TControl>` или
`IFactory<TControl, TArguments>` и передавайте реестр сессии или через DI.

Именуйте части, к которым обращаются поведение, стиль или проверка. При
подключённом генераторе прямые вызовы `Named("Имя")` с константным C#
идентификатором дают типизированные свойства-расширения в отдельном статическом
классе для верхнеуровневого View без параметров типа. Генератор читает
inline-фабрику `Content(...)`, объявленную в конструкторе. Для
`UiControl<TControl, TData>` частью остаётся `TControl`. Сам View может быть
обычным классом. Части разрешаются через реестр живого View после
принятия дерева. NuGet-пакет Argentis подключает анализатор автоматически,
в том числе транзитивно; при сборке из исходников используйте analyzer
`ProjectReference`. Для ручной отписки сохраняйте подписанный экземпляр.

Оформление View и контролов объявлять через `IViewStyle<TView>`: корень, явно
выбранные типизированные части и типизированные семантические роли. Динамические
элементы помечать ролями. Каждый вложенный View имеет собственную область стилей;
не обходить его внутреннее дерево из родительского стиля. Theme содержит общие
цвета, шрифты и размеры. Стили могут использовать Theme, но не изменяют состояние
модели, не запускают команды и не удерживают экземпляры View в общих сервисах.

В inline `Content(...)` `.WithRole(CounterViewRoles.Count)` экспериментально
выводит типизированный токен из типа элемента. Стиль использует тот же
`CounterViewRoles.Count`. Для ролей только вне inline-дерева используйте
`[ViewRole<Text>("Count")]` на `partial`-классе `IViewStyle<TView>`.
Совпадение определяется экземпляром токена, не строкой.

Приоритет значений: local/binding → Style элемента → стиль View → Theme → default.
В Fluent-разметке оставлять композицию и осмысленные локальные переопределения;
общие цвета/отступы/шрифты не дублировать поверх вынесенного стиля. Замена/снятие
стиля и смена Theme обновляют существующие элементы, сохраняя фокус, выделение,
прокрутку и введённые данные. Полную перестройку дерева при каждом обновлении
ViewModel не использовать; динамические поддеревья меняются адресно.

ViewModel, style и `IFactory<TView>` регистрировать через DI; фабрика создаёт View
на UI owner thread, окно/родитель владеет View, dependencies заимствуются согласно
их lifetime. Сами контролы создаются View через Fluent API/конструкторы. Подписки
View снимаются при Dispose, ViewModel не освобождается заимствующим View.
Автоматическая миграция всех прежних consumers не требуется.

#### Регистрация View и вложенная композиция

Для оконного View `.View<TView>()` или `.View<TView, TViewStyle>()` регистрирует
сгенерированную `IFactory<TView>`, не сам View. `UsePresentation<TView>(...)`
получает его из этой или явной фабрики. Регистрации модели следуют типам
параметров конструктора; стиль `IViewStyle<TView>` опционален.

Для постоянного дочернего View принимайте его конкретный тип в конструкторе
родителя, зарегистрированного через `.View<…>()`. Генератор вызовет
`IFactory<TChild>`; зарегистрируйте ребёнка через `.View<TChild>()` или явную
фабрику. Интерфейсный параметр разрешается из DI напрямую. Неприсоединённый
ребёнок освобождается при сбое активации или `Dispose` родителя; после принятия
владение передаётся дереву.
[Схема подключения](TrueMoon.Alloy.Hosting/README.md#вложенные-view-из-di).
