# Заявки приложений к TrueMoon

Принято 07.11.2026 для параллельной разработки Studio и фреймворка.
Это входящий контур [планирования](../PLANNING.md), дополняющий планы владельцев
модулей. Наличие заявки означает запрос потребителя; срок, приоритет и API
определяет владелец модуля после разбора.

## Размещение и ответственность

Каждая заявка — отдельный каталог
`docs/requests/<module>/<UTC-date>-<consumer>-<slug>-<uuid8>/Request.md`.
Модули: `core`, `cobalt`, `enerit`, `mithril`, `alloy`, `engine`, `nom`.
Идентификатор не требует общего счётчика или редактируемого индекса. Список
заявок — содержимое каталога модуля; его PLAN содержит постоянную ссылку сюда.

Автор приложения сначала сверяет API используемого пакета, текущие исходники,
план модуля и существующие заявки по capability. Непроверенный сценарий,
отсутствие функции в старом пакете и воспроизведённый дефект различаются явно.
При наличии подходящей задачи автор добавляет ссылку/новое свидетельство,
а не вторую независимую реализацию того же требования.

После публикации `Request.md` сохраняется как исходный запрос. Уточнения автора
пишутся отдельными файлами `Notes/<UTC>-<consumer>-<uuid8>.md` с ссылками на
исходную заявку и предыдущую заметку. Автор заявки изменяет свой проект;
реализация движка, его активная очередь и STATUS принадлежат агенту модуля.

## Состав Request.md

- Устойчивый ID, дата, приложение и версия пакета, модуль, capability для поиска дублей.
- Сценарий пользователя, фактическое ограничение и минимальный пример/пути исходников.
- Что уже проверено; что ещё неизвестно; влияние на потребителя и временное решение.
- Требуемое поведение, критерии приёмки, совместимость и ownership/lifecycle.
- Возможные варианты реализации с открытыми вопросами; предложенное API не считается согласованным.

## Параллельная работа в общей рабочей копии

1. Публиковать полный запрос под новым уникальным именем: сначала подготовить
   файл в своём рабочем каталоге, затем создать новый каталог заявки и атомарно
   переименовать подготовленный файл внутри того же тома. Не перезаписывать
   существующие заявки; перед публикацией ещё раз проверить дубли по capability.
2. Перед выбором работы агент модуля читает свой каталог и существующие
   `Claim.json` / `Decision.md`. Для принятия владения создаёт `Claim.json`
   через `FileMode.CreateNew` / `O_CREAT|O_EXCL`. В нём — owner/agent или task ID,
   branch/worktree, UTC и область работы. Если файл уже есть, координировать
   продолжение с указанным владельцем; второй исполнитель ту же заявку не начинает.
3. Владелец записывает `Decision.md`: `needs-info`, `accepted`, `deferred`,
   `duplicate`, `declined` либо `completed`; основание, owner, ссылка на task ID
   основного модульного PLAN и на проверки. `Request.md` при этом не меняется.
   Для принятой задачи единственный подробный план реализации остаётся у модуля.
4. Общие PLAN/STATUS редактирует владелец соответствующего этапа: перечитать
   актуальный файл непосредственно перед правкой, сохранить соседние изменения,
   проверить SHA исходной версии перед атомарной заменой. При изменившемся SHA
   заново согласовать патч с актуальным содержимым. Старую копию целиком не сохранять.
5. Заявка закрывается только с ссылкой на реализацию, версию пакетов и фактические
   проверки. Studio отдельно фиксирует проверку обновлённого consumer.

Claim не имеет автоматического срока истечения: долгое время файла не доказывает,
что агент закончил работу. Передача владения требует явного согласования и записи
в Decision/Notes. CreateNew координирует одну общую файловую систему; независимые
клоны должны согласовать владельца через используемые проектом issue/PR или
другой общий канал до начала реализации. Локальный файл не является распределённой блокировкой.

Новые каталоги/заявки не требуют правок общего PLAN/STATUS. При межмодульной
зависимости основной модуль и ссылки назначаются в Decision, без дублирования
подробных задач. Публикация заявки не разрешает автору приложения менять код движка.
