# Формат планирования TrueMoon

Принят 2026-10-09 при разделении общего плана и планов модулей. [Общий план](PLAN.md), [общий статус](STATUS.md).

## Уровни и область ответственности

| Документ | Что хранить |
| --- | --- |
| `docs/PLAN.md` | Цели TrueMoon, карта модулей и зависимостей, сквозные сценарии, порядок развития, общие критерии выпуска |
| `docs/STATUS.md` | Краткая сводка модулей, общие блокеры и ближайшие действия; ссылки на локальные статусы |
| `docs/<module>/PLAN.md` | Границы модуля, цели, архитектура, этапы, зависимости и собственные критерии готовности |
| `docs/<module>/STATUS.md` | Текущее состояние реализации, датированные проверки, ограничения и следующий конкретный шаг |
| `docs/<module>/HISTORY.md` | Подробная история изменений, экспериментов, команд и результатов, когда она перестаёт помещаться в текущий статус |

План ведётся по функциональному модулю, а не по каждой сборке. Генератор, адаптеры и примеры входят в план соответствующего модуля. Alloy/Argentis, Rendering.Skia, Platform.Silk и Alloy.Hosting составляют одно UI направление. Группа Core объединяет bootstrap, Contracts и общие Core utilities; её название не означает, что всё размещено в сборке TrueMoon.Core.

## Содержание плана модуля

1. **Границы:** входящие проекты, ответственность, внешние зависимости и то, что относится к другому плану.
2. **Цель:** контрольный пользовательский сценарий и ожидаемый результат.
3. **Архитектура и решения:** принятые контракты отдельно от вопросов, которые ещё предстоит определить.
4. **Этапы:** устойчивые идентификаторы, результат, зависимости и критерии завершения.
5. **Готовность:** проверки поведения, ошибок, lifecycle, поставки и документации.
6. **Дальнейшее развитие:** направления после первой рабочей версии без превращения их в требования текущего выпуска.

Новые планы Core/Cobalt/Enerit/Mithril являются первичным roadmap. Наличие задачи не утверждает, что её API уже согласован или реализован. Конкретные контракты уточняются перед соответствующим этапом. Согласованный UI план сохраняет прежние идентификаторы1–5, K1–K9 и PA1–PA10.

## Содержание текущего статуса

- Дата и вид последней работы: код, документация, чтение исходников или запуск проверок.
- Реализация: что найдено или изменено; отдельная колонка для проверок.
- Проверки: дата, команда или ссылка на запись, конфигурация, результат и точная область вывода.
- Блокеры и ограничения: подтверждённые препятствия отдельно от непроверенных сценариев.
- Следующий шаг: конкретная задача и требуемое окружение.
- Ссылка на подробную историю; длинный журнал не копируется обратно в STATUS.

Использовать состояния «запланировано», «реализовано», «частично», «проверено на указанной конфигурации», «нужна исходная сверка проверками», «заблокировано указанным условием». Реализация не равна проверке. Наличие тестового проекта, version suffix alpha или успешный build не доказывают готовность.

## Общие и локальные задачи

Детальная задача имеет один основной план. Общий roadmap ссылается на неё и фиксирует межмодульную зависимость. Например, DI lifetime принадлежит Cobalt, app startup/rollback — Core, связь этих механизмов — общему integration этапу. UI focus/input остаётся в Alloy/Argentis; процессный lifecycle не переносится в UI план.

Build всего solution и проверки всех тестовых проектов относятся к общему статусу. UI статус может ссылаться на общий build и хранить собственные GPU/publish/consumer результаты. Ошибки другого модуля учитываются в его статусе и общей сводке; в UI они указываются только при влиянии на UI интеграцию.

В текущем статусе предыдущий запуск всегда называется предыдущим и сохраняет дату. Документационная правка не создаёт нового passing результата. Исторические failures не объявляются исправленными без соответствующей проверки.

## Правила обновления

После работы обновлять STATUS затронутого модуля. Общую сводку менять при изменении межмодульных блокеров, готовности или порядка работ. Решения и критерии менять в PLAN явно с датой и основанием; простая реорганизация документов не отменяет требований.

Накопленные подробные записи переносить в HISTORY с сохранением содержания и дат. Пути PLAN/STATUS сохранять как постоянные точки входа; проверять относительные ссылки. HISTORY для новых модулей создавать после появления фактических записей, без пустых журналов.

Общая версия пакетов сейчас задаётся Directory.Build.props. Независимое планирование модулей не меняет автоматически номера версий, public API, target frameworks, структуру solution или порядок поставки.
