# Aether source observer performance

The measured 2026-11-04 baseline, results and setup attempts are recorded in
[engine HISTORY](../../docs/engine/HISTORY.md#ed6b2e4-observer-performance-2026-11-04).

Measures the existing production `EditorSourceWatch` using a descriptor obtained
from an actual `GameBuildCompiler` frozen Build. No copied census, internal access,
fabricated descriptor, native UI or runtime child is involved. The compiler and
observer factory are registered in App DI; each case owns and drains its observer.
Production scheduling remains **10 s after completion / 5 s cooperative budget**,
with default 250 ms debounce, 1 s maximum debounce and at most 32 watchers.

From `src`, run the six cases sequentially:

```powershell
pwsh -NoProfile -NonInteractive -File ManualTests/AetherSourceWatchPerformance/Run.ps1 -EvidenceDirectory TestResults/ObserverPerformance-MyRun
```

The runner builds Release with a unique binlog, then runs each graph with native
notifications disabled and enabled in separate processes. `-SkipBuild` reuses the
already built Release harness and records its hash. `-Profiles control,files` can
be supplied as an array when calling the script from PowerShell. Existing
verification/report evidence is never overwritten. Frozen compiler jobs retain
their normal SDK stdout/stderr diagnostics. A case deadline only kills the owned
child tree; production observer limits are unchanged.

| Fixture | Graph | Generated files | Generated bytes |
| --- | --- | --- | --- |
| control | Four non-overlapping projects, diamond references | 64 C# × 1 KiB | 64 KiB |
| files | Same four-project diamond | 2560 C# × 4 KiB | 10 MiB |
| bytes | Same four-project diamond | 128 non-Compile data files × 1 MiB | 128 MiB |

Project files, the game entry and exact framework-contract inputs add to those
counts; the bytes fixture also has four small C# marker files. All tree members,
including non-Compile data, are covered by the existing capture/observer policy.
This separates large-byte observation from aggregate compiler reference/source
copy limits without changing any production limit. Each report contains the **actual** captured file/tree/probe counts,
descriptor, baseline identities and bytes. Generated projects and artifact jobs
live in a short unique OS temp directory outside checkout ancestors; the report
records that directory and preserves it for inspection. The source-only scope
does not include managed packages, network paths, cold-disk caches or physical UI.

Each case performs two seconds of inert `NoBuild` sampling, the initial
observation and three complete steady observations at the ordinary interval. It
then edits a late generated file without changing length or mtime, measures
publication latency, restores the byte, verifies the `Changed` latch during two
seconds of idle, and awaits actual Stop/drain twice. A final hash census confirms
fixture restoration. A budget failure is recorded as `Unavailable`; it is not
fixed by increasing the deadline or converted into a successful Same sample.

The measured windows exclude generation, compilation, explicit setup GC and final
source hashing/report IO. They include the **whole target process and sampler**;
CPU and allocations are not falsely attributed to the census alone. The inert and
latched idle windows calibrate sampler/background overhead. No forced collection
or priority/power/cache/OS changes occur within observation windows.

* Wall-time bounds come from `IsScanning` / `ObservationVersion` snapshot reads
  with a requested 5 ms delay. Actual scheduling gaps are reported. A short scan
  may fall entirely between samples; its lower bound is then zero. These are
  observed bounds, not a real-time guarantee or an exact method profiler.
* CPU is process `TotalProcessorTime` delta in milliseconds and percent of **one
  logical core** over the entire cycle (including the 10 s wait). Windows CPU
  accounting granularity affects small samples. Allocations and GC counts are
  process-wide managed counters.
* `ReadBytes` / operation deltas are
  [GetProcessIoCounters](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-getprocessiocounters)
  logical process IO, including cache and metadata effects, **not physical disk
  traffic**. Compare them with descriptor bytes on complete Same passes.
* Private/working-set peaks are sampled every 100 ms, including window endpoints,
  via [GetProcessMemoryInfo](https://learn.microsoft.com/en-us/windows/win32/api/psapi/nf-psapi-getprocessmemoryinfo).
  They are whole-process samples and may miss shorter peaks; retained memory from
  build/setup remains part of the process baseline. They are not observer-only
  memory or overall OS peak counters. Process.Refresh is deliberately avoided
  because calibration showed material sampler overhead.

`Run.ps1` records SDK/OS/CPU, commands, exits, all production source/loaded framework
DLL/harness hashes and checks that these inputs did not change during the matrix.
`report.json` contains raw windows, initial/steady state, detection, budget and
cleanup results. Unit, GPU, packaged consumer, full-solution and release acceptance
remain independent checks; successful measurements do not establish their status.

After the matrix, generate the compact table and validate report/input hashes:

```powershell
pwsh -NoProfile -NonInteractive -File ManualTests/AetherSourceWatchPerformance/Summarize.ps1 -Verification TestResults/ObserverPerformance-MyRun/verification.json
```

## Managed thread-time profiling

`Profile.ps1` reuses the exact harness/production DLLs recorded by a completed
baseline. It verifies all baseline hashes before/after collection, waits for Build
and the initial observation, confirms each owned PID with `dotnet-trace ps`, then
attaches during the first polling wait. Default collection is two `files` repeats
and one `bytes` control, polling only, with no source or scheduling change.

Install the pinned Microsoft tool into an ignored local directory and run:

```powershell
dotnet tool install dotnet-trace --tool-path TestResults/ObserverProfile-tools --version 10.0.750501 --configfile NuGet.Config
& ./ManualTests/AetherSourceWatchPerformance/Profile.ps1 -TraceTool TestResults/ObserverProfile-tools/dotnet-trace.exe -EvidenceDirectory TestResults/ObserverProfile-MyRun -BaselineVerification TestResults/ObserverPerformance-MyRun/verification.json
& ./ManualTests/AetherSourceWatchPerformance/AnalyzeProfile.ps1 -Speedscope TestResults/ObserverProfile-MyRun/files-1/observer.speedscope.json -Output TestResults/ObserverProfile-MyRun/files-1/analysis.json
```

Repeat the analysis command for `files-2` and `bytes-3`. Existing output files are
preserved. The collector uses `dotnet-common,dotnet-sampled-thread-time`, a 64 MiB
buffer and a 30 s duration, with NetTrace and local Speedscope conversion. The
target continues its ordinary complete benchmark and cleanup after tracing stops.
Collector/target arguments, PID/start timestamps, tool version/hashes, discovery,
stdout/stderr and topN reports are retained. Live stdout is read with compatible
FileShare.ReadWrite; failed setup attempts must be kept separate from valid traces.

The analyzer checks event ordering and balanced stacks, filters intervals containing
an actual `EditorSourceCensus` or its directory-cache/pin helper frame, conserves their weight across disjoint
categories, and also reports overlapping inclusive/exclusive method weights.
**Sampled managed thread time is not whole-process CPU usage or a complete async
wall-time breakdown.** Unresolved native/inlined frames retain their resolved caller
context; kernel/driver attribution and lost-event accounting need separate evidence.
Profiler overhead means these durations do not replace the unprofiled baseline.

The descriptor-based `ValidationModel` counts the legacy uncached ValidatePath ancestor
loop on a clean full pass, including repeated visits. It is a comparison model,
not the optimized pin/check count or an instrumented syscall count; retries can add visits. Compare old and new traces with the same analyzer version, saving fresh output files. The repeatable profiling
finding and its scope are recorded in
[ED6b.2e.4a](../../docs/engine/HISTORY.md#ed6b2e4a-observer-profile-2026-11-04).
Tool provenance: [Microsoft dotnet-trace](https://www.nuget.org/packages/dotnet-trace/10.0.750501)
and [official collection/report documentation](https://learn.microsoft.com/en-us/dotnet/core/diagnostics/dotnet-trace).

## Per-attempt directory cache

The production scanner now retains at most 256 positive ancestor validations per
attempt. A retained directory has a root-first chain of Windows handles opened
with LIST_DIRECTORY|READ_ATTRIBUTES, read/write sharing without delete sharing,
and OPEN_REPARSE_POINT. Handles fence directory rename/replacement while permitting
child-file edits and membership changes. If optional pin access fails, that chain
uses the original fresh metadata checks; metadata-only access remains supported.
No missing path or error is cached. Overflow also uses fresh checks.

Before Same, every retained ancestor is checked again by path. Persistent reparse,
access, type or disappearance changes are rejected. Sharing does not freeze ACLs
or attributes; this remains sampled observation, not an atomic filesystem snapshot
or detection of transient changes that have already reverted. Every attempt owns
and disposes its handles before retry/completion. Full byte hashing, tree membership,
probes, retry budgets and scheduling limits remain in force.

Run a new six-case matrix before collecting new profiles; an old baseline manifest
intentionally rejects changed production hashes. Use the same analyzer for old and
new traces and retain all prior output. Results are recorded in
[ED6b.2e.4b](../../docs/engine/HISTORY.md#ed6b2e4b-observer-directory-cache-2026-11-04).

## File reader and metadata lane

The scanner uses one synchronous, no-follow local-file handle per known file on
the existing background worker. Its initial attributes/length/write time come from
that opened handle. Reads use the census buffer directly, without a second stream
buffer, IOCP registration or a queued continuation per small-file read. After EOF,
a fresh path query verifies attributes/length/write time. Full hashing remains
mandatory; this is neither a content cache nor an atomic filesystem snapshot.
Read/write/delete sharing permits editor saves. Reparse points are rejected at
open and at the final path check. IO cancellation is cooperative between reads;
Stop still awaits actual completion before disposing the handle.

File/probe metadata uses one WIN32_FILE_ATTRIBUTE_DATA query. Only native missing
codes 2/3 produce absence; access/sharing/other errors propagate. Absent probes
avoid thrown exceptions, and every probe query remains fresh. Injected test streams
keep independent before/after path metadata checks.

For this lane, reanalyze the directory-cache baseline and new traces with the same
current analyzer. It recognizes EditorSourceFile helper frames and the framework
OSFileStreamStrategy constructor. The open category includes opened-handle metadata
and disposal; it is caller attribution, not an isolated CreateFile syscall timer.
Earlier conservative category outputs remain immutable. Exact run results belong
to [ED6b.2e.4c](../../docs/engine/HISTORY.md#ed6b2e4c-observer-file-io-2026-11-04).

## Opened metadata and prepared path

The opened reader now queries FILE_BASIC_INFO plus file size instead of the legacy
volume/file-ID record. Unsupported basic/size APIs (native1/50/87) retain the old
query; access/sharing/IO failures still propagate. The extended native path is
prepared once per reader and reused only as a name for fresh final metadata queries.
No metadata result, source bytes or handle survives its original owner/attempt.
Injected metadata delegates keep precedence over the prepared-name path.

Compare this lane with the completed file-IO baseline and analyze both trace sets
with the same analyzer revision (including ReadOpenedMetadata). Exploratory native
open-only experiments are separate from whole Observer measurements. Current
results belong to [ED6b.2e.4d](../../docs/engine/HISTORY.md#ed6b2e4d-observer-native-open-2026-11-04).

## Bounded native open batches

For at least 256 known files, the default census stages at most four native opens
at a time. Directory validation stays serial on the coordinator; worker jobs only
open files/read initial metadata. Every job finishes before batch hand-off. Reads,
SHA256 and cumulative byte budgets stay sequential with one shared census buffer.
Missing/errors are consumed in descriptor order, so a future staged error cannot
replace an earlier proven Changed. The batch closes all unconsumed readers on
Changed/failure/cancellation and before retry, probe checks or final revalidation.
Stop awaits actual opens, including an in-progress synchronous OS call.

Small graphs and injected open/metadata/directory hooks retain the serial path.
Four short native jobs add scheduling/allocation overhead; end-to-end measurements
must justify this tradeoff. No persistent handles, new NT API or public scheduler
options are introduced. Fresh metadata/full hashing and sampled-observation bounds
remain in force. Parallel thread-time weights cannot be treated as wall-time speedup.
Compare with the completed ED6b.2e.4d baseline using the same current analyzer,
including EditorSourceOpenBatch worker frames. Results belong to
[ED6b.2e.4e](../../docs/engine/HISTORY.md#ed6b2e4e-observer-open-batches-2026-11-04).
