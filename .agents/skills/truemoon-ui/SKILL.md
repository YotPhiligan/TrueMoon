# UI TrueMoon на Argentis и Alloy

Собирай View так, чтобы по Fluent-дереву читались порядок блоков, видимые
состояния, привязки и действия пользователя.

## Источники

- Начинай с [AGENTS.md](../../../src/AGENTS.md) в каталоге `src` и текущего
  [статуса Alloy](../../../src/docs/alloy/STATUS.md).
- Для визуальных решений используй [дизайн-код](../../../src/docs/alloy/DESIGN.md).
  Для выбора проверки используй [UI_TESTING](../../../src/docs/alloy/UI_TESTING.md).
- При композиции, миграции или генерации частей открывай
  [пример обозревателя](references/editor-hierarchy.md). Сверяй спорный API
  с исходниками и [контрактом UIA1f.11](../../../src/docs/alloy/PLAN.md#uia1f11-contextual-content).
- Импортируй `TrueMoon.Argentis.Views` для `View` и `ui.*`, `Styling` для
  `IViewStyle` и его правил, `Input` для команд и `IInputContext`; это
  подпространства `TrueMoon.Argentis`, а не новые пакеты. Корень нужен для
  `UiProperties` и сгенерированных Fluent-расширений контролов. Остальные типы
  ищи по [карте UIA1i](../../../src/docs/alloy/PLAN.md#uia1i-argentis-structure).
- Для подключения пакетов и регистрации экранов см. [Hosting](../../../src/TrueMoon.Alloy.Hosting/PACKAGE.md).
  NuGet доставляет анализатор Argentis автоматически, в том числе через Hosting;
  `ProjectReference` из исходников требует явной ссылки на анализатор.

## Проектирование и реализация

Перед разметкой перечисли зависимости экрана: вложенные View и зависимые
контролы, ViewModel, стили, общие команды, сервисы, презентеры и их фабрики.
Для каждой выбери регистрацию в DI приложения и владельца экземпляра.
Не создавай эти зависимости через `new` в разметке и не передавай ей resolver.
[Правило композиции через DI](../../../src/AGENTS.md#ui-composition-di).

1. Определи основной сценарий и действия с клавиатуры. Учти пустое состояние,
   ошибки, недоступные действия и узкий viewport, когда они влияют на экран.
   Расположи блоки в порядке чтения и взаимодействия. Подписывай действия и
   задавай `AccessibleName` там, где видимого текста недостаточно.
2. Объявляй дерево в конструкторе через `Content(data, ui => ...)` или
   `Content(ui => ...)` для View без модели. Создавай контролы через
   `ui.Create<TControl>()` и шорткаты `ui.Text(...)`, `ui.Button(...)`,
   `ui.HStack(...)` и `ui.VStack(...)`. `Fill()` отдаёт элементу долю
   остатка по оси стека. Описывай дерево и обработчики в одном файле.
   Действия в одну-две строки оставляй в дереве, более длинные размещай
   ниже. Возвращай корень, созданный этим `ui`, и включай в него каждый
   контрол, полученный из контекста. Для готового поддерева используй `SetContent`.
   Для закрытой детали без зависимостей от приложения используй локальную
   типизированную `IFactory` через `ui.Create(factory[, arguments])`. Не меняй
   реестр сессии ради детали; фабрика возвращает новый неприсоединённый контрол.
3. Держи draft, доступность команд и ошибки в Data/ViewModel, а фокус,
   прокрутку и жизненный цикл контролов — во View. Читай текущий фокус из
   `IInputContext.FocusedElement`, а для восстановления используй `TryFocus`:
   недоступная цель не должна отнимать фокус. Политику выбора цели оставляй
   во View. Для чтения используй `Bind`, для редактирования — `BindTwoWay`
   или точечный сгенерированный
   метод вроде `BindValueTwoWay(data => data.SearchText)`. В цепочке
   `UiControl<TControl, TData>` селектор следует за текущим `IDataContext<TData>`.
   Для другого источника передай его явно.
   Для готовой команды текущей модели используй `WithCommand(data => data.FindCommand)`,
   для общей стабильной команды — `WithCommand(command)`. Кнопка и клавиатура
   выполняют одну команду.
   Для открытия popup или изменения фокуса используй
   `.OnActivated((button, input) => ...)`; не сохраняй заимствованный `input`.
4. Оформляй экран в `IViewStyle<TView>`. Выбирай `Root`, `Part`,
   `TypedPart` и `Role` по цели правила. Для динамических элементов
   используй семантическую роль. Цвет, шрифт и размеры бери из Theme там,
   где они общие. Приоритет значений сохраняй в порядке
   local/binding → Style элемента → стиль View → Theme → default.
   В inline `Content(...)` используй `.WithRole(CounterViewRoles.Count)`,
   в стиле — `styles.Role(CounterViewRoles.Count)`. Генератор экспериментально
   выводит тип роли из контрола. Если роль применяется только вне inline-дерева,
   объявляй её через `[ViewRole<Text>("Count")]` на `partial`-классе стиля.
   Правило применяется ко всем помеченным элементам, включая добавленные позже.
5. Именуй части, которые нужны поведению или требуют устойчивого доступа в
   проверках; для элементов, нужных только стилю, предпочитай `WithRole(...)`
   и `styles.Role(...)`. Не дублируй сгенерированную часть ручным полем или
   CLR-свойством с `null!`. При замене публичного CLR-свойства укажи в миграции
   импорт namespace View, пересборку потребителей и потерю instance getter для
   reflection и ABI.
   Генератор находит прямые вызовы `Named("Имя")` в inline-фабрике
   `Content(...)` и выпускает свойства-расширения типа самого контрола.
   Часть с типом, доступным только в сборке, получает `internal`
   свойство-расширение; для публичной части фабрика должна объявлять
   публично доступный тип.
   Читай части на UI owner thread, начиная с `OnContentPrepared()`: дерево уже
   принято, а attach-уведомления и первый layout ещё впереди. Вложенное View хранит
   имена в собственной области. Если генератор не подключён, используй
   `GetRequiredPart<T>()` или `TryGetPart<T>()` после подготовки дерева.
   Часть одного режима читай только в нём или через `TryGetPart<T>()`.
   Не сохраняй скрытые контролы ради smoke: проверяй реальный пункт меню
   или кнопку и результат команды.

Для новых Fluent-методов следуй схеме `Property(value)`, `On<Event>(handler)`
и `With<X>(...)`. Сеттер вызывает штатный путь установки, `On` подключает
обработчик события, а `With` объявляет композицию или связь. Владение и
время жизни определяются контрактом операции. Планируемые методы помечай
как предложения, готовые примеры составляй из доступного API.

Для постоянного ребёнка родителя, зарегистрированного через `.View<…>()`,
принимай конкретный тип View. Зарегистрируй ребёнка через `.View<TChild>()`
или зарегистрируй `IFactory<TChild>` вручную. Генератор вызывает эту фабрику
до конструктора родителя. Обычный интерфейс модели или сервиса не меняет
семантику DI. Если View нужен позже, несколько раз или с аргументами,
принимай `IFactory<T>` либо `IFactory<T, TArguments>` явно.
[Вложенная композиция](../../../src/TrueMoon.Alloy.Hosting/README.md#вложенные-view-из-di).

Для строк наблюдаемой коллекции регистрируй `.ViewWithArgs<TRowView, TItem>()`;
внедри `IFactory<TRowView, TItem>` и передай `rows.Create` в `BindItems`.
Строка данных передаётся в единственный параметр точного типа `TItem` из
выбранного конструктора, а не регистрируется в DI. Остальные зависимости и
опциональный стиль работают как у обычного View.
[Пример списка](../../../src/TrueMoon.Alloy.Hosting/README.md#динамические-строки-из-фабрики).

## Владение и проверка

- `.View<TView>()` или `.View<TView, TViewStyle>()` регистрирует сгенерированную
  `IFactory<TView>`, не `TView`; `UsePresentation<TView>(...)` вызывает её на UI
  owner thread. Фабрика применяет опциональный DI-стиль через `ViewCreation.Prepare`.
  Неприсоединённых детей освобождает неудавшаяся активация или родитель при
  `Dispose`. После передачи владения за детей отвечает дерево.
  Сессия выполняет фабрику из `Content(...)` при первом attach и применяет
  стиль после `OnContentPrepared()`. При reattach готовые контролы
  сохраняются. Деревом владеет окно или родитель, а модель и стиль
  заимствуются. Для своего контрола регистрируй `IFactory<TControl>` в DI и
  подключай `UseControlFactory<TControl>()` в `UseAlloy` или `UsePresentation`.
  Вариант с аргументом — `UseControlFactory<TControl, TArguments>()`; меняются
  только указанные ключи, остальные остаются у выбранного реестра сессии.
- Прикладной презентер подключай в Hosting через `UsePresenterFactory<TControl, TState>`:
  фабрика `IFactory<IElementPresenter<TState>>` приходит из DI, а созданным
  презентером владеет сессия. Контрол о нём не знает. При ревью проверь,
  что в обработчиках ввода, layout и рисовании нет обращений к контейнеру.
- Наблюдай текущую модель на срок attachment через
  `.ObservePropertyChanged(handler, synchronize)` в цепочке контрола или
  `this.ObservePropertyChanged(this, handler, synchronize)` на View.
  Обработчик уведомлений идёт через очередь UI. `synchronize` читает
  состояние при attach и смене контекста. Подписку с ручным снятием
  привязывай к тому же экземпляру контрола.
- Проверяй затронутое поведение через `UiSession` и маршрутизируемый ввод.
  При смене темы проверяй сохранение фокуса, прокрутки и черновика там,
  где они есть. При изменениях подписок проверяй detach, reattach и
  `Dispose`. Добавляй CPU raster для визуальных изменений и native профиль
  для сценариев, зависящих от окна или GPU.
